Lane a, from the phase head b7463a07 (T3.2, T3.3 with T3.19, T3.8, T3.14, T3.15 and T3.18 landed), under the structure design's T3.4 section (fixes C, E and F).

## What changed

- **Contract v28** (design choice 3; T3.8's `ProviderChoice::Sql.namespace` and `DescribePart::Namespace` kept, T3.4's own variant of that name dropped):
  - `Relation.columns` and `Relation.filter`, opaque SQL text the core never reads, with the capability `derived_relations`; a derived relation for any provider without it, a host provider's included, is refused by name (rule `derived_relation`) where every request is routed;
  - the capabilities `sample_rows` and `neighbor_lookback`, `SampleEntities.rows` and `SamplerMemo.rows`, for the old client's `TABLESAMPLE` percentage and `_by_fkey` look-back;
  - `TableKey.unique` (P2-T2.2-3), counted as the reference counts a key the source keeps unique, in the shared key counts of every dialect;
  - `ProviderError.refuses_expression` (overnight decision 4), set by the host from the SQLSTATE class 22 or 42, for T3.5's view columns;
  - the data layer's built-in-only flags in `ProviderCapabilities` (P2-MID2-2), the `DataLayer` methods and dialect hooks gone;
  - the capability `keys_optional`: a provider whose catalog may fail to read keys, whose columns and keys are then read apart and a failed key or foreign-key read taken as none, as `DatabricksTable` carries on without them;
  - FX-6, the binding's test messages reading the crate's version.
- **One namespace model** (fix C): each dialect declares its namespace depth (DuckDB and SQLite 0, Postgres 1, Databricks 2) and how its source compares names, replacing T3.18's boolean; a namespace of more parts is refused by name.
  A source leaving a part to the connection inside one it gives (`DatabricksSource(conn, catalog='main')`), or any part of a dialect that reads every table under its full namespace (Databricks: `DatabricksSource(conn)`, `schema='shop'`), has its namespace read once at the run's start (`current_catalog()`, `current_schema()` for the parts left), and every relation read under the parts answered, so a declared foreign key's fully named table is found.
  Where the schema read each relation is a fact of the schema that read it, kept by relation (`HeldSchema.read_under`); on the host it is held on the old route's own engine reading, `EngineTables.readings()` (`Schema._read_under` a read-only view, `Schema._keep_readings` the one place it is written), so it has exactly the lifetime of `Schema._engine_tables`, site by site:
  - `Schema.__init__` sets `_engine_tables` to none: a schema built anew holds no reading;
  - the old route's `Schema.from_source` (`schema.py`, `schema._engine_tables = read`) and the core's (`_rust/schema.py::build`, a new `EngineTables()`) each make a new one, the core's holding where it read the tables;
  - the relational materializer makes one where there is none before its first read (`relational.py:555`); `Schema._keep_readings` makes one there likewise when the core first says where it read a table;
  - `snapshot()`, and `copy.copy`, which calls it, share the same object, so a reading either adds reaches the other;
  - `__setstate__` (pickle, `copy.deepcopy`) restores the pickled object with its readings, none where the state holds none; an object pickled before it held readings starts empty (`EngineTables.readings`);
  - `contract/fixtures/request-pickles/write.py` leaves `_engine_tables` out of its fixtures, and the readings with it;
  - nothing else creates, replaces or clears `_engine_tables`, and no reading is filtered: `held_schema` writes every reading, a table held now or not, and an edit's answer, the readings as handed, is stored whole.
  `materialize` reads a table where the schema read its relation while the source's own parts agree with it (`DataLayer::keeps`), and every other table where the source and its session say now.
  A `materialize` that asks for them (`Materialize.progress`, which the Python host sets) says the old route's two moments as steps that ask nothing, the one mechanism:
  - `inputs_checked`, where the old route makes `EngineTables` (`relational.py:555`): past every refusal of the request (no entities, the batch size, a reserved column name, too many entities, the shapes, the schema's consistency) and before the run reads anything, its session's namespace included; the host then makes the schema's engine reading, a source's schema alone (`relational.py:554`);
  - `tables_located { read_under }`, where the old route keeps its tables (`EngineTables.keep`, `materializers/sources.py:72` and `:79`): once the run has read the catalog of every table the schema holds no reading of, under the session's namespace, and before it samples (its first count); the host then keeps each, a source name it holds left as it is.
  A run that fails or is interrupted before a moment has said nothing of it; one past it has said it. The old route's `from_source` writes at `schema.py:1321` and `:1352`, which the core's `from_source` matches with the namespace it described under.
  An edit answers the schema's readings as it was handed them, and the host stores what the core answers.
- **The `databricks` dialect** (fix E): one `SqlDialect`, only what is Databricks's own: backtick quoting, three-part relations, the catalog statements with the old client's `lower(?)` parameters, key sets through `posexplode(from_json(?, ...))`, `TABLESAMPLE (p PERCENT) REPEATABLE (seed)` with the percentage as the reference's `str(float)` writes it (KO3-41), `QUALIFY ROW_NUMBER()` per seed, `_get_num_rows`'s count, a derived relation as `_quoted_source_name` reads a metric view's table, and a table whose catalog found a column named like a session word (`user`) read through its columns in every read, as `_quoted_source_name` reads it; its catalog reader types each column as `_to_dtype` does and refuses a metric view read as a table.
- **The core**: a table keeps the one-part name its caller gives it (the catalog's canonical names are not adopted); each table's columns the catalog read named on every later read of it for a provider declaring derived relations, marked as found (`Relation.found`); a declared foreign key's table found by its name read under the source's namespace, dotted; a declared unsupported type refused by name (P3B-1); for a provider declaring `sample_rows` or `neighbor_lookback`, every table's rows counted once for a materializer, the sample naming its rows, and each neighbor read by a foreign key looking back as `_by_fkey` does.
- **The host** (fix F): `Source.kind` and `Source.namespace_parts()` in `sdm_connectors`; one `providers.for_source` keyed on them; `_routing` keyed on kind, the `databricks-sql` and `databricks-spark` routes core-routed, defaults `old`; `DatabricksSqlProvider` and `DatabricksSparkProvider`, one implementation, the key set as one JSON text written as `_dumps` writes it, chunked as `_chunk_rows` chunks it; a Databricks failure's SQLSTATE read as `sql_state` reads it, through the provider's `error_fields` hook.
  The `Provider` protocol and the plan rules every SQL provider applies (`PlanNotRun`, the plan and key-set checks, the Arrow key-set reader) live once in `sdm_connectors.providers`, with the rule that one relation name binds one key set; the run loop names `Provider` for annotations only, so a core route over frames runs without the connectors package.

## Deviations and what is left

- SQL text that differs from the old client's where the result is the same, for review against the recorded statements: the key set's columns named by the core's seed names (`batch`, `key`, `time`, `start`, `end`) where the reference writes `__KUMO_BATCH__`, `__KUMO_ID__`, `e` and `s`; a lookup's duplicates removed in SQL where the reference removes them after the fetch; no outer window bounds (the reference binds them for data skipping, which the live timing run measures).
- Carried rows left for the packages now reworking their areas: P2-T2.8c-2 (answered parts, the host's results: T3.16), P2-MID2-3 (the unread-columns warning's fields: T3.17's wording), P2-MID2-4 (typed option values: T3.16's plain-data inputs), P2-T2.2-1 (a lookup's seed meanings as request fields, which rewrites every dialect's lookup goldens).
- A relation marked `found` that renames, computes or filters its columns is refused where every request is routed; a guard from a catalog read is never replaced by the schema's fewer columns.
- Every catalog read guards its table with all the columns the catalog found, as the old client does (`describe_source`, and `materialize` where it reads facts the schema lacks); a `materialize` of a schema whose columns all carry their facts reads no catalog and guards each table with the columns the schema holds, so a session-word column the schema leaves out is read by name there, which differs from the old client only if that column changes during the run (round 2's Claude P2-3: the held schema carries facts of its own columns only).
- `contract/fixtures/databricks/capture.json` and `reference-statements.json` are synthetic unit fixtures, frozen: written once with an offline stand-in warehouse over DuckDB, which is removed (owner B-lite; round 1's Codex P1-6); `compare.py` beside them keeps only the comparison of the core's statements with the old client's. C-1's live recording replaces both.
- The live recording of Databricks' core route (structure design step 3) waits for the owner's renewed login and the write guard.

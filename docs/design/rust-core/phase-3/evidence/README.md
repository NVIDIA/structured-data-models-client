## Lessons from final validation

These observations describe the work so far; they do not imply that Phase3 is accepted.
They supplement the earlier [migration lessons](../../learnings.md).

- Separate client defects from fixture, environment and evidence failures before changing code.
  The missing Spark DuckDB dependency failed the test loader before the first fixture, not the client.
  Batch genuine fixes, get both exact code approvals before checks, and reuse only independently proven unaffected evidence.
- Observe individual cloud-task attempts, not only the parent job.
  The failed Spark task was automatically retried with the same broken environment while its parent still said RUNNING.
  Preserve the original failure, inspect each attempt and cancel only an owned retry proven to repeat an unfixed failure.
- Define what SQL equivalence means before the final draw.
  Matching successful predictions does not by itself prove equal source rows, counts, metadata or error behavior.
  Conversely, different internal labels or query grouping need exact semantic evidence and the actual owner-approved scope, rather than copying an old query's incidental shape.
- Separate different external replies from changed client behavior.
  Eight apparent schema-order differences came from differently ordered Databricks replies to identical SQL without ORDER BY; both clients preserved their own provider's order as required.
  Independent Snowflake samples also required comparison on identical rows and contexts before making an accuracy claim.
- Plan storage applicability and cloud dependencies before starting a frozen validation attempt.
  SQLite cannot preserve stored NaN, and several backends cannot preserve nanosecond timestamps.
  Record the exact unsupported pairings and actual runtime identities without changing the original case values or pretending that setup failures are product refusals.
- Keep one coordinator responsible for the tracker, and consume completed handoffs before waiting.
  Each handoff needs an actual owner and next action; a completed review should immediately enable its next authorized check or landing.
  Extra reminders and monitoring systems did not substitute for this ownership, and the overactive reminder was removed.
- Keep evidence identities honest while avoiding redundant work.
  CI, native binaries, warehouse observations and documents keep their actual producing commits and hashes.
  An unaffected documentation or fixture correction does not justify repeating every live campaign, and the final documentation remains separate from the tested source tree.

The existing handbook, run-start register, actual job-attempt metadata and source-pinned receipts support these observations.
They add no new gate, automatic compatibility exclusion, monitoring service or permission to rewrite failed evidence.

# Main-to-Rust audit: changes to reconcile in Phase 6

Snapshot: **2026-11-04 00:14 UTC**, after fetching the four remote branches.
Compared fetched main `1c5e2e71d` against Phase 6 `2e29a56a9`; no product changes, merges or rebases were made.

## What matters

**Rust-core is only one main commit behind, but ancestry did not guarantee that every older fix survived the migration.**
The audit found four concrete product gaps: new gradient explanations, temporal-link PQL batch limits, DuckDB 2 admission/copy behavior, and PostgreSQL keyless JSON/XML ordering.
Only the temporal-link limit was reproduced as an incorrect public request boundary; the PostgreSQL issue is source-confirmed and still needs a live reproduction.
Two additional CI improvements and narrow regression-mapping checks are listed separately below.

## Decisions and remaining verification

- Old engine `PredictionRecord`/SHA256 graph logging from `2992c4b36` is absent, but the old public facade did not call that instrumented engine prediction route.
  Explicitly retire that engine utility or decide to add facade diagnostics; do not claim an established user-facing regression or replace Rust's unrelated sampler memo hash.
- Cross-run source caching was intentionally replaced with per-run refresh (`sdm-core/src/describe.rs:774`).
  Do not restore it just to reproduce old catalog-read counts.
- Retired Python engine/PQL packages, C++ wheel jobs and intermediate release publishers are intentional replacements, not missing APIs.
- `d90d0a802` still needs explicit regression mapping for empty-result ID-column shape and repeated planning not mutating earlier request metadata IDs.
  No defect was established; its generated API/PQL validator edits were checked as nonbehavioral.
- PostgreSQL timestamp precision/null handling has Rust counterparts and fractional/nanosecond tests; add/map the exact original timezone-offset-plus-null case before calling that original regression fully verified.
  UTC normalization differs from preserving offset spelling; the initially suspected precision loss was ruled out for PostgreSQL.

## Goal

Phase 1a builds the contract, the first core crates, the binding and wheel, the runners, the comparator, the ratchet and the CI checks, and proves them on S0 (PQL validation).
Phase 1b runs one hard journey end to end on the new architecture: DuckDB `Schema.from_source` to `materialize` to `predict` to the result, through the contract and the data provider interface, in Python and on the pure-Rust test host, over the 40 fixed cases of [phase-1b-inventory.yaml](../phase-0/phase-1b-inventory.yaml).
Work starts thin: a minimal contract and wheel, one S0 case through Python and Rust, then the first DuckDB regression journey, and only then the general tooling; the early journey reduces risk, and does not merge early or relax the 1a exit (decision C5).
The phase ends with an evidence pack and the owner's go or no-go: go merges 1a and 1b into `rust-core` and starts Java's S0 work; no-go means repairing the first attempt in place, or stopping.

- `contract/` sits at the root because it belongs to neither language.
- The Python host package is `_rust`, not `_core`, so it cannot be confused with a name the reference guard probes.
- `dependencies.md` in this folder records one row per dependency and per hand-written substitution: use a library, port a defined algorithm, or keep in the host, with the measured reason.

### Workspace rules

- Edition 2024, `rust-version = "1.97"`, toolchain pinned to 1.97.0 as the minimum supported Rust version, `Cargo.lock` committed.
- `panic = "unwind"` stated explicitly, so panics can be contained.
- `unsafe_code = "forbid"` in workspace lints and at every domain crate root; only `sdm-py`, `sdm-testkit` and later `sdm-jni` relax it, locally, for Arrow FFI; as built at T1.8, `sdm-py` denies `unsafe` and has none.
- Clippy runs with `-D warnings`, each `#[allow]` carries a one-line reason, and every `.rs` and `.toml` file carries the SPDX header the hygiene check enforces.
- No `#[ignore]`, `skip`, `xfail` or `continue-on-error` under `rust/`, `scripts/rust_core/`, the client tests touching `_rust` or `_native`, or the Rust and contract CI jobs; a CI step fails on one (T1.10c).

### Contract

- `ColumnType` is the closed type set of plan section 3; `ColumnType::from_arrow` is the only way in, and anything else is refused with `kind: unsupported, code: UNSUPPORTED_TYPE` naming the column and the Arrow type.
- The scope manifests' cell vocabulary is generated from that enum.
- Operations are a versioned, serde-tagged enum; Phase 1 needs `validate_query`, `describe_source`, `materialize` and `predict`.
- `Step` has exactly three variants: `Fetch` (a batch of typed data requests, each with the Arrow schema it expects back or a discovery marker), `CallModel` (the body an attachment) and `Done`; no step asks the host for language behavior.
- Every byte buffer and Arrow table that crosses (fetch results, key sets, model bodies, request state, results) is an attachment named by `AttachmentId`; the sender numbers what it sends, core-to-host ids are unique within a run, and host-to-core ids are scoped to one message (E2).
- **The 64 KB control cap bounds the envelope only.** Any field whose size grows with user input (query text, `QuerySchema`, `SourceDescription` in a `start` or a `Done`, later view definitions) travels as a bytes attachment holding UTF-8 JSON of the same serde type; no inline field grows with column, table or row count (contract v3, H5; supersedes HOST-1).
  As built at T1.7b (E15), that also moves `describe_source`'s table list and declared keys (`SourceSpec`) and `RequestState.query` into attachments; a `start` names each with the kind it must be, and one id named twice is refused.
- **Every message the core writes** (steps, including a `Fetch` with its plans and expected schemas, results, errors and warnings) that would pass the cap travels whole as an attachment named by a minimal control message; nothing is truncated, refused or dropped for size (H7, revising E13's cap clause).
  As built at T1.7b (E15): the minimal message is `{"message": "attached", "attachment": n}`, and the attachment travels with it, numbered in the run's own sequence (a `start` that made no run numbers it 1); a run's warnings since the last call go as one message.
- Errors are `{kind, code, message, fields, cause, retryable}` with closed kinds; `code` is an exhaustive `ErrorCode` enum with SCREAMING_SNAKE names (PQL diagnostic codes stay strings inside `PqlDiagnostic`), so each host's match has no catch-all arm; `retryable` defaults to false and is carried from provider and transport errors; each host maps every `(kind, code)` through one reviewed table, tested exhaustively, never reading message text (H6).
- `ProviderError` and `TransportError` carry kind, `retryable`, SQLSTATE and vendor code only: v3 drops their `message` and free-string `code`, since drivers quote values there.
  `ErrorCode` lists the 22 codes the contract had as strings; a warning's code stays a pattern-checked string, since no warning is promised before T1.6b's D4 warning. A POSIX `TZ` local zone that does not parse is refused at `HostRun::start` with `INVALID_REQUEST` naming `facts.local_zone`; an IANA local zone is resolved when a run first reads it (T1.6b).
- Warnings travel on their own channel, in order; no contract string names a Python or Java class.
- Every scalar in a control message is a tagged object with its value as a JSON string (integers per width, `d128` and `d256` with precision and scale, floats with shortest round-trip text and non-finite values, temporal counts with unit and zone), so nothing passes through a double; the encoder never writes what the decoder refuses (E4).
- `materialize`'s seed is an integer of any size as signed hexadecimal text (`^-?0x[0-9a-f]+$`, no leading zeros), which avoids CPython's 4,300-digit `str(int)` limit; the core refuses a negative seed and per-backend ranges (RS-7) with `INVALID_REQUEST`, never the decoder (H7).
- `HostFacts` (the clock, a `ts` in UTC; the local zone, an IANA name or a POSIX `TZ` string; the zone lookup roots in order with their versions; the platform padding rule) is part of every operation; locale is not a host fact, and the core reads none.
- State such as `RequestState` is typed and carries its version; an unknown version is refused by name; runs and Arrow buffers have defined owners and release rules.
- The JSON Schema is generated by `schemars`, committed, and locked by hash in `contract.lock`; the hash covers a projection that strips only the annotation keywords (`description`, `title`, `examples`), so a doc comment needs no bump while a property named `description` does (H7).
  The projection keeps names under `properties`, `$defs` and the other name maps, and data under `enum`, `const` and `default`; the hash is the SHA-256 of the projection as compact JSON with sorted keys, computed the same way by `schema_lock.rs` and `contract_lock.py`.
- The contract version is independent of the package version; within a phase each bump is a decisions row (E7 for version 2, H5 for version 3) (H4).
  Entries not yet merged into `rust-core` are working versions: the lock holds one working entry, rewritten at each in-phase bump; "never rewritten" applies to entries present at the merge base with `rust-core`, so a phase lands as one bump.
  At T1.7b the lock collapses its v1 and v2 entries into that one entry, version 3 in `sdm-contract-3.json`, and `sdm-contract-1.json` and `sdm-contract-2.json` are deleted; no historical decoder is promised (H25). The validated-query lock (E8) follows the same rule; `Span`'s rows from 1 change its shape too, so it moves to working version 2 in `pql-validated-query-2.json`.
  `contract_lock.py` checks the entries at the merge base with `rust-core` and at most one working entry, not the branch's history, since working entries are rewritten.
- Version review covers behavior as well as shape: a change to validation, units, ownership, defaults or error meaning bumps the version even when the schema is unchanged; host and core ship together and refuse any other version before execution (H25).

### Key sets

- A key set crosses the core/host boundary as an Arrow attachment referenced by ID from a typed data request; control JSON carries only its descriptor, never the keys (decision Q1).
- The DuckDB provider owns the physical binding (for example, registering the attachment as a relation), and both hosts implement the same semantics.
- Tests prove a key set whose serialized contents exceed 64 KB without raising the control cap, and exact binding of uint64 above int64 max, `decimal128(38, 0)` and scaled decimal keys.
- The decimal tests use values that collide as float64 (for example `0.100000000000000001` and `0.100000000000000002` at scale 18): distinct keys stay distinct through binding, join and result association, and a forced decimal-to-float conversion in that path fails the test (H22).
- Exact identity is not exact arithmetic: where the reference converts a numeric target or sums labels in float32 (PK-2), that conversion is intentional and stated, not a key defect.

### Data access

- `sdm-contract::data` holds the request vocabulary, the capabilities and the port: `trait DataLayer { fn plan(&self, request: &DataRequest, capabilities: &ProviderCapabilities) -> Result<FetchPlan, CoreError> }` (H14).
- `FetchPlan` is one or more `SqlStatement`s run in order, or a typed pass-through of the request to a host provider, together with the Arrow schema the whole plan returns; the host answers one request with one attachment.
- `sdm-data` implements it; SQL dialects are internal to `sdm-data`, and the wire names a source's backend only for `sdm-data` to interpret.
- `CompositionRoot` holds one `Arc<dyn DataLayer>`, built by `sdm_host::default_root()`; swapping the data layer replaces that one value (proved in Phase 2). A non-SQL source is a host provider answering the typed requests; Phase 2 swaps the `DataLayer` value and adds that provider.
- Domain crates do no I/O and hold no `Asker`; only `sdm-core`'s operation bodies await, and `Asker::fetch` takes a `DataRequest`.
- Dependencies: `sdm-core` → `sdm-request` → `sdm-engine` → `sdm-schema` → `sdm-contract`; `sdm-core` → `sdm-data` → `sdm-contract`; `sdm-core` → `sdm-pql-interim`, from its adapter only; `sdm-host` → `sdm-core`, `sdm-contract`; `sdm-wire` → `sdm-contract`, used by `sdm-request`; `sdm-py` → `sdm-host`, and `sdm-contract` for types only (E21: T1.8 also depends on `sdm-core`, removed in T1.9); `sdm-testkit` (dev-only) → `sdm-host`. No crate below `sdm-core` depends on it, checked by `l0_deps.py` from T1.10c.
- A fetch result is complete: the host drains every driver batch of a request into one Arrow attachment; multiple batches and an empty result keeping its schema are tested on both hosts; paging is Phase 2.
- The Phase 1 vocabulary is the existing requests, with these changes from T1.11a (an in-phase bump, H4):
  - `Describe` also returns each table's indexes, which feed the reference's "Missing N indices" warning;
  - `TimeBounds` takes a list of `(table, column)` and returns one row per pair, as the reference's single `UNION ALL` does;
  - `SampleEntities` gains `columns` and `filters`, as the reference projects columns and adds `IS NOT NULL` filters;
  - `Neighbors { table, key, columns, seeds, window, per_seed, order }` (H15):
    - `seeds` is a key-set attachment with role-named columns `key`, `batch` and zero or more seed time columns, zone-less `timestamp[ns]`;
    - `window` is optional: `{column, lower: Option<SeedBound>, upper: Option<SeedBound>}`, with `SeedBound { seed_column, inclusive }`; a row whose window column is NULL is not returned when a window is set;
    - `per_seed` is an optional row limit per seed; `order` is a `TieBreak`, required when `per_seed` is set and otherwise absent, so the result is unordered;
    - the result carries `batch`, and, when ordered, is ordered by `(batch, TieBreak)`; result helper columns use the reference's names (`__kumo_batch__`, `__kumo_matches__`), or the initial `compare-policy.yaml` maps them by role before T1.11e;
  - `Lookup`, one row per seed key, with the batch and the match count.
- The reference's two neighbor fetches are both `Neighbors`: `_by_fkey` is `upper = anchor, inclusive`, `per_seed = n` with its `TieBreak`; `_by_time` is `lower = start, exclusive` (when the window has a start) and `upper = end, inclusive`, with no limit and no order. `sdm-engine` computes `anchor + DateOffset` for `end` and `start` with civil arithmetic before it builds the seeds.
- `TieBreak` is `Vec<{column, as_timestamp, descending, nulls_last}>`, built by the core from the reference's rule: when the table has a time column, the first term is `CAST(time AS TIMESTAMP)` descending (`as_timestamp` set on that term only); then the primary key; without a primary key the remaining terms are every non-list column by name, the raw time column included, as the reference's SQL sampler does on DuckDB; with none, the foreign key; all terms NULLS LAST.
- Times compare in the source's own `CAST(column AS TIMESTAMP)` wall clock, against seed times in zone-less `timestamp[ns]`.
- `Lookup` returns any one row of a key that several rows hold, as the reference's `ROW_NUMBER()` without `ORDER BY` does; the core compares such rows only as members of the matching set, and refuses a scored key held by more than one row, as the reference refuses it.
- Every field of a request is honored or the request is refused with a typed error; no flag is ignored. A provider that does not declare an optional request it is sent gets `UNSUPPORTED_REQUEST` naming the request; Phase 1 has no in-memory fallback.
- A declared capability that fails is an error, never silently replaced.
- `sdm_core::start` takes `Arc<dyn Zones>` (the trait in `sdm-engine::time`), implemented by `sdm-host`'s resolver and cached per lookup roots and versions; a future Java host passes the bundled database with its version recorded.

### Time

- Inside the core every instant is `Instant(i128)`, nanoseconds since the UTC epoch, and every span is `Span(i128)`, nanoseconds (F3).
- Columns stay Arrow arrays with their own unit, zero-copy; `Instant` and `Span` exist for scalars and transiently inside per-row kernels.
- They are built only from an Arrow temporal column with its unit, a contract `ts` or `dur` scalar, the PQL date reader, or civil arithmetic in `sdm-engine::time`, and leave only by checked conversion to a named unit, which returns `VALUE_OUT_OF_RANGE`, never saturating or panicking.
- A zone-less timestamp is wall clock read at offset 0; a zoned one converts to its UTC instant through the zone, with T1.25 vectors.
- A `Span` is a fixed duration only; a calendar offset (`DateOffset`) is a `{months, days, nanos}` value applied by civil arithmetic in `sdm-engine::time`.
- No raw `i64` meaning time crosses a function boundary; `jiff::Zoned` exists only inside a zone-conversion call; no unit-generic type family.
- At or past `jiff::Timestamp::MAX` (9999-12-30T22:00Z), conversion uses civil arithmetic and offsets; an instant is never refused because `jiff` cannot hold it (E6).
- T1.25 adds vectors at both ends of the int64 microsecond range and at 9999-12-31 in every vendored zone.

### Core, host and binding

- `sdm-core` has one `Run` type: operation bodies are `async fn`s over an asker handle, polled once per step, with no executor and no threads.
- States are `Ready`, `AwaitingFetch`, `AwaitingModel`, `Finished`, `Cancelled` and `Poisoned`; an illegal call returns a `protocol` error and never panics; after `cancel`, every call returns kind `cancelled`, `RUN_CANCELLED`; id overflow ends the run with `INTERNAL_ERROR` (E5).
- `sdm-host` is plain Rust and the only API a binding calls: `HostRun::start`, `next`, `reply`, `cancel`, `take_attachment` and `take_warnings` take and give control messages as bytes with the attachments each names (E13); from T1.7b an error comes back the same way, as an `error` control message with its attachments (`Outgoing`), never as a Rust value only a Rust caller could read.
- Each call is contained by `catch_unwind` (a panic poisons the run and returns `INTERNAL_ERROR` with `fields.panic = true`), and a concurrent call on the run gets `RUN_BUSY`.
- A host message must attach exactly the ids it names, as the kind it names, or it is refused with `INVALID_MESSAGE` before the run sees it.
- **Schema match (H16)** is two checks: (a) each batch must match its attachment's declared schema (column count, order, names, types and required metadata) before admission; (b) each admitted fetch result must match the outstanding request's expected schema, stored with the request, before domain code sees it; a discovery request establishes the schema and later batches must match it; a mismatch is `PROVIDER_SCHEMA_MISMATCH`, never a dropped, relabelled or filled column.
- **Admission (B-D6, H16)** lives once in `sdm-host` and widens losslessly, since refusing a type the reference accepts is a regression: `large_*` to small forms; `timestamp`, `duration` and `time32` at `s` or `ms` to `us` by checked multiplication; `date64` to `timestamp[us]`, whatever its values; `utf8_view`, `binary_view` and list views to `utf8`, `binary` and `list`; `fixed_size_binary` to `binary`; `float16` to `float32`; `decimal32` and `decimal64` to `decimal128`; `large_list` and `fixed_size_list` to `list`; `dictionary<K, large_utf8>` to `dictionary<K, utf8>`, and a dictionary of any other value type to its value type; `run_end_encoded` to its value type (E17, from T1.7d).
  Admission keeps the received Arrow type beside the admitted one, so inference sees what the source returned; required field metadata and a dictionary's categorical meaning are kept in the canonical schema.
  A batch is split between rows where cumulative offsets would pass int32; a single value larger than int32 offsets can hold, or a value the admitted type cannot hold (an `s` or `ms` timestamp past int64 microseconds), is `VALUE_OUT_OF_RANGE` naming the column and the type received; each refusal of a type or value the reference accepts has a register entry (HOST-2) approved by the owner; a refusal ends the run (E13).
  As built at T1.7c: check (a) is in `sdm-host`'s admission and compares each batch's names, types and field metadata exactly with the declared schema, and refuses nulls in a column declared non-nullable; check (b) is in `sdm-core`'s `Run::submit_fetch`, which keeps each pending fetch's expected schema and compares names, order, closed-set types, the metadata the request requires and nulls where it expects none; both refusals end the run. `time32` is admitted as `time64[us]`, a dictionary of non-text values is decoded with `arrow-select`'s `take`, and the received schema is kept as `ArrowData::received`. A batch past the capacity is split by halving the rows tried until each part fits; `admit_with_capacity` sets a smaller capacity for tests. The type families still refused, generated by the admission tests and listed in HOST-2, are `interval`, `run_end_encoded` and `union`.
  As built at T1.7d (E17): a `run_end_encoded` column, with run ends of `int16`, `int32` or `int64`, is decoded with `arrow-select`'s `take` to its value type, which is then admitted as any other column, honouring the array's slice; before `take` builds anything, the int32 offsets a decoded run-end or dictionary column would need are checked against the capacity, so such a batch splits between rows and only a single value past it is `VALUE_OUT_OF_RANGE`; check (a) counts its nulls, which are its values', as nulls. The type families still refused, generated by the admission tests and listed in HOST-2, are `interval` and `union`.
- Native-to-Arrow tables stay in each host.
- `sdm-host` resolves each zone, in any case, through the host's lookup roots in order, then the bundled copy, and records the source and version under the zone's IANA spelling (E3).
- **Threading:** the core starts no threads and holds no global state; a run is used from one thread at a time (`RUN_BUSY` otherwise); runs are independent; `sdm-py` releases the GIL for every core call and holds it only while touching Python objects; importing `_native` starts no thread and installs no logger, signal handler or global pool.
  No Rust lock is held across a `tracing` event or an Arrow release callback, and none is taken while the GIL is held; this covers the zone cache. The one exception is a run's busy lock (E20): a non-blocking try-lock, held across the call it guards, events included, never waited on; a second call gets `RUN_BUSY`.
- **Test-only operations:** `sdm_contract::test_ops`, built only with the `test-ops` feature, which a shipped build leaves off, and skipped by the generated schema, so the lock is the same with it on or off. From T1.7b they drive a fetch, a result, an error and warnings of any size through `HostRun::start`, their inputs as attachments; T1.7c adds the panicking one and T1.8 the logging one.
- **Logging (H8):** `tracing` in Rust; `sdm-py` bridges it to Python `logging` with `pyo3-log`, initialized at the first core call; the Python host resets `pyo3-log`'s level cache at each run start, so a logging configuration change takes effect; tests drive a known event through a real core call (the test-only operation, built only with the `test-ops` feature, which the wheel leaves off) and assert exactly one Python record at the expected level and target, and a GIL-deadlock regression test runs on that path.
  As built at T1.8: the bridge is `pyo3_log::try_init`, run once under the GIL by the first `Run` call through a `PyOnceLock`; if another `log` logger was installed first, the core's events go to it and `reset_log_cache()` does nothing. pyo3-log leaves an exception a `logging` handler raised pending in the thread's error indicator, so after every core call the binding takes any pending exception: an `Exception` is reported through `sys.unraisablehook`, as `logging` reports its own handler failures, and the call's answer is delivered; anything else, such as `KeyboardInterrupt` or `SystemExit`, is raised in place of the answer, which is dropped, and the run stays where the core left it, so a step `next` gave is not given again and the next call meets the run's following state (for the test-only `log` operation, `RUN_FINISHED`). A handler that calls into its own run gets `RUN_BUSY`. A run's busy lock is held across the call it guards, events included, but is only ever tried, never waited on (`RUN_BUSY`), so no thread blocks on it while another logs.
- **Diagnostics (H17):** no input value or credential reaches a `CoreError`'s message, fields or cause: a contained panic keeps its location, not its payload text, and is reported out of band by `contain()`, never detected from an error field a host can set; a codec error names the position and category, not the offending text; a provider error keeps SQLSTATE and vendor codes as fields and leaves the driver's message text out.
  The Python host raises with `from None` and puts the driver's exception class, SQLSTATE and vendor code in the error's fields, so no traceback carries driver text; where a case shows today's chained cause, that shape change is that case's deviation.
  `sdm-host` installs a panic hook once, at the first `HostRun::start`, that writes only the location for a panic inside a contained call and defers to the previous hook otherwise.
  As built at T1.7c: the hook is installed at the first contained call, which for a binding is its first `HostRun::start` (tests that build a run directly reach it through their first call); `contain()` returns a `Failure` whose `panicked` flag, not `fields.panic`, poisons the run; the error carries `fields.panic` and `fields.location`; a codec or attachment error carries `category`, `line` and `column`, never the text read.
- `sdm-py` is a thin PyO3 module over `sdm-host`: it passes Arrow through the PyCapsule interface only, which the `pyarrow>=14.0.1` floor guarantees (E16), raises one `_native.CoreError`, and passes model bodies as bytes attachments; it makes no semantic callbacks into Python, while Arrow export and release callbacks are allowed and counted.
  As built at T1.8: `_native` holds `Run` (`start`, a static method, then `next`, `reply`, `cancel`, `take_attachment` and `take_warnings`), `CoreError`, `ArrowStream`, `reset_log_cache()`, `CONTRACT_VERSION` and `TEST_OPS`, typed by `sdm_client/_native.pyi`; a control message crosses as `bytes` and its attachments as a `dict` by id, each `bytes` or Arrow. `CoreError` carries the `error` message as `control` and `attachments`, with `kind` and `code` read from it, and its text is `kind: code` alone. An Arrow attachment in is any object with `__arrow_c_stream__`, checked before `arrow-pyarrow` reads it, so pyarrow's `_export_to_c` is never reached; one out is an `ArrowStream`, a class of the binding with `__arrow_c_stream__` (a requested schema is refused) and `__arrow_c_schema__`, since `arrow-pyarrow`'s own export goes through pyarrow's `_import_from_c`; `sdm-py` has no `unsafe` code. An Arrow attachment the binding cannot read reaches `sdm-host` as `Unreadable`, named apart from the attachments it could (`HostRun::reply_reading`, `HostRun::start_reading`; `reply` and `start` are these with none), with nothing of the failure's text. The message and its whole set of attachments are checked first, as any reply's or start's are, an unreadable one standing in as Arrow data of its id, so an attachment the message does not name is `INVALID_MESSAGE` and the run is unchanged; a reply the run does not await gets the run's own refusal. Only then is a producer's failure (an exception from `__arrow_c_stream__`, a stream it cannot start, such as one whose schema has a type arrow-rs cannot import, or an error its stream reports) the provider's error, `PROVIDER_ERROR` with `retryable` false since nothing of its text is kept, handed to the run as the fetch's outcome; and a batch Arrow cannot build in its stream's own schema, such as one with nulls in a column declared without them, is check (a)'s `PROVIDER_SCHEMA_MISMATCH` and ends the run. No Phase 1a operation names an Arrow attachment in its `start`, so there an unreadable one is always the envelope's refusal. A stream's batches carry its schema, so check (a)'s other cases cannot arise through the binding and stay `sdm-host` tests. An object without `__arrow_c_stream__` is a `TypeError`. Counting export and release callbacks arrives with T1.17's exact-release check. The test-only operations gain `log` (one `INFO` event with target `sdm_core::test_ops`, then a held call), `abort`, and a fetch's `echo`, which returns the admitted data as an attachment named by the result's `data`. The binding's tests are `rust/bindings/sdm-py/tests`, run against an installed wheel named by `--native-build`; the clean-import test counts environment reads through `os.environ` and, by a preloaded `getenv` shim built from `getenv_shim.c`, through the C library, ignoring only the dynamic loader's own `DYLD_` and `LD_` variables.
  An interrupt raised inside a Python-backed producer while it makes a batch reaches the binding as the stream's own error, as pyarrow reports producer errors, so it counts as a producer failure and the interrupt itself is not re-raised; the binding cannot tell the two apart without our own FFI code.
- The pure-Rust host calls `HostRun`, so its fetched data passes the same admission and schema match as Python's.

### Observations and comparator

- An observation (`sdm-observation/1`) is JSON in which every scalar uses the contract's tagged-string encoding; payloads keep their raw bytes and a parsed form with numbers as decimal text; result tables are Arrow IPC files referenced by SHA-256.
- Every compared field names its acquisition point: public output, HTTP request or response, driver-boundary capture, or core `Step`.
- `contract/availability.yaml` fixes, per runner and field, available or unavailable; a field is never fabricated or treated as equal; a field a locked check requires that is unavailable fails that check; an `available` field missing from an observation is an error; downgrading a field, or adding one as unavailable, is a relaxation (H2, H13).
- `core` fields: Arrow types, stypes, keys, time column, data requests, statements and the result each returns, payloads, the pre-presentation Arrow result, error kind, code, fields and cause chain, and warnings by code in order.
- `host` fields: pandas dtypes, Python error and warning classes, `StructuredDataError.code` and the `to_pandas()` result, through which the reference's result is compared, never as an Arrow table rebuilt from pandas.
- `rust-host` and `python-core` are compared on `core` fields, as core-issued requests and core SQL (provider binding statements are compared with the reference only, as diagnostics), by a `contract-python` step that reads `rust-test`'s observation artifact; Python runners are compared on `host` fields and on the `core` fields that one projection in `run_python.py` obtains, as the runtime cells say.
- An `identity` envelope (runner, cell, platform, commit, `_native` SHA-256, reference commit, corpus and input digests, contract version, DuckDB version, per-zone database source and version) is validated separately and excluded from digests.
- `scripts/rust_core/compare.py` prints the first difference per field with its path, under the rules in `contract/compare-policy.yaml`.
- Exact fields keep null apart from NaN, `-0.0` from `0.0`, decimal precision and scale, temporal unit and zone, nested validity, field metadata and duplicate rows; message text never gates, and the inventory's message fragments are reported for information.
- Payloads are compared parsed with lossless numbers, excluding only the approved UUID and nondeterministic field paths; results by Arrow schema and values, with row order only where the operation defines it; raw payload and IPC hashes verify artifact integrity only.
- **SQL (H9, as the owner revised it):** against the reference, the comparator gates on the statement count (setup excluded) and each statement's result: Arrow schema and rows, with row order only under a total `ORDER BY`, and batch boundaries never; typed parameters are reported, not gated; only draws documented as non-repeatable use the named invariants of `random-streams.md`, and deterministic seeded draws keep result-row comparison; the reference's raw SQL text and bindings are diagnostic only; the core's SQL text is pinned by the DuckDB goldens (T1.30), and a golden update never replaces a register entry. T1.11e confirms the rule with the measured counts of `base.regression`.
- Nondeterministic draws follow `random-streams.md`: membership, cardinality and named invariants instead of row equality, with exclusions only for named field paths.
- No Phase 1 case overrides the default seed, so its draws are deterministic; no fetch replay is built; common-input comparison is a Phase 2 prerequisite for PostgreSQL and a Phase 3 one for live warehouses, and until then those downstream comparisons are listed as unproven, not equal by invariant (H24).

### Reference observations and the gate

- Reference results are committed under `contract/reference/<reference-commit>.jsonl`, with the reference's frozen environment in `contract/reference-env.txt`, so CI compares without running the reference; `gate.sh` regenerates them on the reference machine when the reference, its environment or a case input changes, and at T1.20 and T1.36, and compares the semantic projection, not bytes or hashes, with identity checked separately (decision B-D8).
- `contract/baselines/<cell>/<runner>.jsonl` holds each case's projected observation and its digest. Digests cover only the platform-independent projection `compare-policy.yaml` marks, and CI ratchets that projection; the remaining fields are baselined from the reference machine and ratcheted only by `gate.sh` there.
- **The checkpoint** is the last reviewed landing a candidate builds on (H2, as the owner revised it). At package start, resolve the last reviewed phase-branch tip to `BASE_SHA`, before advancing that branch, and compute `CHECKPOINT_SHA = git merge-base CANDIDATE_SHA BASE_SHA`; record both immutable SHAs with the candidate evidence and pass that same `CHECKPOINT_SHA` to local and owner-merge gate invocations. CI works the checkpoint out the same way and never reads it from evidence: on a topic branch `BASE_SHA` is the phase-branch tip at run time; on a phase-branch push it is the push's previous tip, and a push to the phase branch lands exactly one package. Never recompute it from a phase-branch ref that already contains the candidate; a non-bootstrap candidate equal to its checkpoint fails. Landing fast-forwards the phase branch to the exact tested candidate. If the phase branch advanced after `BASE_SHA`, the package is rebased onto the new tip and gated again with `BASE_SHA` reset to that tip and its new `CHECKPOINT_SHA` recorded; a saved checkpoint is reused only for a different integration commit whose merge base with the phase tip is still that checkpoint (for example, after adding a trailer). There is no tag, no promotion step and no separate accept commit.
- **The checkpoint's harness judges (H2):** each gate run, in CI or `gate.sh`, checks the checkpoint out into a separate worktree, overlays only the checkpoint's observation projection and capture (`contract/runners/run_python.py`, and the case loader and observation writer in `sdm-testkit`) onto the candidate, and runs the checkpoint's `compare.py`, `ratchet.py`, L0 scripts and expectations against the candidate's observations; the candidate's own harness result is reported only. The pure-Rust host, its providers and the scripted endpoint are candidate code, protected and named in the `Reviewed-by:` trailer, because they grow with the contract. Lists that may only shrink (`KNOWN_DIFFERING`) live in a data file the corpus test reads from the candidate; the checkpoint's ratchet accepts the file only as a subset of the checkpoint's. The owner's merge-time gate runs `gate.sh` itself from the checkpoint worktree.
- **Bootstrap and evolution:** until T1.14 lands there is no checkpoint harness; the candidate's harness runs, the independent reviewer inspects it, and no acceptance claim is made. T1.14's candidate runs the four fail-first controls before it lands, and from that landing the checkpoint's harness judges. A field or rule the checkpoint's harness does not know is reported, not gated, until the package adding it lands; a new check passes its positive and seeded-negative controls before it lands; a new case has no baseline, meets its reviewed effective expectation on admission and is protected from its landing; a missing baseline for an admitted case is an error.
- **Protected paths:** `contract/protected-paths.txt`, read at the checkpoint, lists the cases, reference observations, `reference-env.txt`, register, comparison policy, availability, L1 expectation files (the PQL corpus and journey queries, zone, stream and hash vectors, vendored tzdata, layout vectors, goldens), the emulation allowlist, `deny.toml`, `clippy.toml`, `ci.yml`, `contract/runners/**`, `rust/crates/sdm-testkit/**`, the corpus test directory, `scripts/rust_core/**`, and `packages/**` except the seam files (`_rust/`, `_routing.py`, `_native.pyi`, the S0 hook in `query.py:_resolve`, the build metadata in `pyproject.toml`).
- A package's landing commit carries a `Reviewed-by:` trailer naming the review run and every protected path the package changes; `gate.sh` fails on a protected change the trailer does not name. Additions and tightenings pass on that review; changing an existing case outcome needs a reviewer-approved register entry; a relaxation needs a decisions row whose status reads "approved by owner" with a date. Decision rows the executor writes never authorize a protected change.
- Stream and hash vectors are never re-recorded to pass a dependency bump (F4).
- Against the checkpoint, a changed digest, a new refusal, a removed case (moving a case to diagnostic counts as removal), or a changed case input fails unless an approved entry in the change names that case, cell, runner, and exact old and new outcome.
- A repair is judged against the effective expected outcome (the reference plus approved deviations); returning to raw reference behavior cannot revoke an approved deviation or regress a protected success without its own approved transition.
- **Deviations are approved when the changed case lands (H19):** each semantic or SQL deviation is recorded and independently approved in the change that first admits that case to acceptance; a refusal of an input the reference accepts waits for the owner; T1.33 reconciles completeness, and is not the first approval point.
- Adding or tightening a comparison rule passes; the checkpoint's ratchet treats a removed rule, an added exclusion, a lowered availability or a field added as unavailable in `compare-policy.yaml` or `availability.yaml` as a relaxation, which needs an owner-approved row.
- **Approval:** the reviewer approves entries (`approved_by: reviewer`, never by the implementer); `approved_by: owner` records only the owner's own written answer; at each check-in and at the merge, `gate.sh` lists every `approved_by: owner` added, every protected-path change, every `KNOWN_DIFFERING` change, and every first-parent landing on `rust-core-phase-1` that has no passing `evidence/gate/<sha>.json` for that exact SHA on the reference machine, since the last check-in; the owner's local merge is the only hard approval; there is no signing machinery.
- **One gate run per work package (H3):** a change is one reviewed work package, not every intermediate commit. The package generates its proposed baselines (`ratchet.py accept`) and the reviewer reviews them with the code; one final gate run judges the package against the checkpoint's baselines and checks that the proposed baselines equal the accepted observations. The package lands only when `evidence/gate/<sha>.json` names the exact landing SHA; one rerun after review fixes is allowed. Landing is the promotion; no successor commit is validated again.
- The first landing with baselines (T1.14) baselines only cases equal to their reference projection on every compared runner; at the go merge the phase branch's baselines become `rust-core`'s.

### Register v2

- `register.yaml` moves to `sdm-register/2` (decision A6): each entry may carry `case_outcomes`, a list of `{case, cell, runner, old, new, summary}`, and `decision_ref` becomes `{file, row}`.
- `register.py validate` checks the schema, unique and never reused IDs, case IDs that resolve to corpus cases or, for entries written before the corpus, the legacy form (a task ID `T<phase>.<n>[a-e]` or an inventory case ID), and the status rules.
- `case_outcomes` are generated by `ratchet.py` from the observations, never written by hand; the reviewer approves an entry once for its one stated meaning, not per case and cell.
- An entry counts only when approved by someone other than its implementer; an entry that refuses an input the reference accepts needs `approved_by: owner`.
- Changed contents under an approved ID count as a new change and need approval again; the ratchet compares entry contents with the checkpoint; no entry can accept a panic.

### Coverage generator

- `scripts/rust_core/coverage.py` implements the rules of [scope-format.md](../phase-0/scope-format.md), checking both manifests structurally but gating only the active language and slice: S0 requires its validation paths and no cells, and Java runtime coverage starts with Java.
- Rule 6 (with all 40 cases): a cell claim names the observed boundary and stage (received Arrow type, admitted type, declared role, inferred role if reached), and a refusal covers its rejected input without claiming a later stage.
- The manifests' `cases` lists are generated (`--write`) and checked (`--check`), never edited by hand.
- `--gate S0` runs in Phase 1; `--gate S1`, which also enforces rule 7, is a Phase 2 obligation.

### Harness scope

- The agreed acceptance capabilities are the runners, the comparator, the ratchet, the coverage checks and the guards and gate around them; a new capability needs the owner's approval (decision C6), and the status page lists every acceptance capability added since T1.1; the owner approved the one-time S0 differential at T1.20 (H11).
- File splits, renames and tests implementing those capabilities need normal review only.
- The status page reports size trends: non-test, non-generated lines of harness and product per crate (`tokei`), with the PQL parser reported separately; unexplained growth triggers a review against the agreed capabilities, not an automatic stop.

## Gates

### Merge rules

- Every candidate that passes its checks is pushed before more work builds on it.
- A work package lands on the phase branch when existing CI and every check activated so far in the task table are green; no activated check is disabled later, and every Phase 1a check is active at T1.20.
- Diagnostic cases run and report in CI but stay apart from the acceptance corpus: they count toward no coverage and set no baseline until matched or approved; a diagnostic case's fields are gating from the landing at which they match; `base.regression` is diagnostic until T1.29, and reaching its result is gating from T1.11e.
- A change to bindings or native dependencies also passes `wheel-smoke` once it is active.
- A type or conversion fix lands only with a public case that failed first.
- Phase 1a does not merge on its own; 1a and 1b merge into `rust-core` together, locally, after the owner's go.
- S0 has no separate slice-done gate in Phase 1: its L3 run and the update from `main` come before any S0 path switches in Phase 3.

### Locked acceptance checks

Locked at T1.1 and amended by the owner on 2026-10-08 (H13, and answers 3 and 5 of re-review round 2), and at the T1.7b check-in (E16, check 3's floor); any later change goes to the owner.

1. 1a exit, run by `gate.sh` on the reference machine: S0 green against the committed reference observations, `python-core` and `rust-host` matching them in `ref-pandas3` (validity and `StructuredDataError.code` in Python, kind and code on the core) and `python-core` equal to `python-old` in the other cells; the L1 corpus green on codes and spans; coverage `--gate S0` passing; no S0 case refuses an input the reference accepts without an owner-approved register entry.
2. 1a exit: the seeded faults and comparator fault tests of T1.19 and the ratchet's seeded checks of T1.14 each behave as stated.
3. 1a exit: the wheel installs and loads in both clean containers of T1.17, including the E16 floor (pyarrow 14.0.1, pandas 2.2.0).
4. 1b exit, the reference comparisons run by `gate.sh` on the reference machine: on all 40 inventory cases, `python-core` and `rust-host` agree on `core` fields; in `ref-pandas3`, `python-core` matches the reference, and in `dbr17-pandas2` it equals `python-old`, on inferred types, keys, time columns, data requests (statement count and each statement's result, as H9 says; typed parameters and raw SQL text are diagnostic), payloads, results, warnings and refusals, or differs only where an approved register entry states that case's cell and exact old and new outcome; a field marked unavailable fails this check; the core's SQL matches the DuckDB goldens.
5. 1b exit: no case refuses an input the reference accepted without an owner-approved entry, and no case panics.
6. Both halves: every activated check is green, and all Phase 1a checks are active from T1.20.

### Process rules

- At most two review rounds per change and per half; the reviewer is a fresh agent that checks code and behavior, not prose; a third round goes to the owner.
- Stop rules: two fix rounds on the same divergence go to the owner; a check failing twice the same way changes method; a phase that keeps finding new work stops for a re-plan; while a blocking question waits for the owner, work narrows to the current task.
- The tracker keeps the stop-rule counters as integers, one row per divergence, check or T1.32 family; a fix round is one batch of fixes after a review verdict requiring changes; a counter reaching 2 is escalated to the owner in the same commit that records it (H20).
- A package's first full review has both reviewers, an independent subagent and Codex, with a scoped brief; a design-checkpoint review of the landed range runs every four or five packages, and is not a review round of any change (E25).
- An agent never sets `approved_by: owner` except to record the owner's own written answer, citing it, and never approves its own entry.
- Reproduce a failure from the installed package before any remote run; Python gates need the Python and pure-Rust checks only.

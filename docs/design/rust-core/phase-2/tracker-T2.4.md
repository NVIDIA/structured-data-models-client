# Phase 2 tracker: T2.4

T2.4 is the combined CI landing: the design's T2.2b (SQLite CI), T2.3b (Postgres CI) and T2.4 (full L4 and L5) in one package (the orchestrator's scope), with the carry that the SQLite and Postgres contract jobs run in every cell and the Postgres provider's test runs with the test-ops build and the Postgres service.
Lane b, on the phase head after T2.3's landing (68f9b8e4), rebased onto T2.19's (dfdd532a).
No separate test author was assigned: the new tests are this package's own, minimal and focused, and the orchestrator decides whether any needs a test author's acceptance test (below).

## What changed

- **`compare.py`, the one judging change** (its own commit, first): off DuckDB, python-core alone in a cell other than the reference's is no H1 pair failure, since python-old does not run there (T2.1a fix 4); its host fields stay reported against the reference, and every core rule still gates it. On DuckDB the pair still needs both runners. `contract/tests/test_t24_cells_off_duckdb.py` (three cases, failing before the change).
- **T2.2b, SQLite** (`ci.yml`): `rust-test`'s SQLite pass, rust-host over every case on SQLite through the dev-only `rusqlite` provider (`sdm-contract-run --database sqlite`), held to the staging rule (`run_python.py legs`) and to python-ref's committed lines moved by the approved entries (`compare.py --database sqlite`), as the contract jobs hold python-core; `cross-host (sqlite)`, the two hosts compared in one `compare.py --database sqlite` run, each against the reference and the two by the core rule, after the same staging check.
- **T2.3b, Postgres** (`ci.yml`): `contract-python (<cell>, postgres)` has python-core record the server's answers to its fetches (`--record-fetches`); `rust-test` hands its build of `sdm-contract-run` on as an artifact, and `cross-host (postgres)` replays the reference cell's recording with it (KO2-20, KO2-60), then compares as on SQLite. The design says `cross-host (postgres)` replays (choice 2, "CI"), and `rust-test` cannot wait for a recording made after the native wheel, so the replay is there, from `rust-test`'s own build: no second build.
- **Every cell** (the carry): `contract-python (dbr17-pandas2, sqlite|postgres)` and `contract-python (floor-pandas2.2, sqlite|postgres)`, sharing the reference cell's steps; the Postgres ones also run the service and loader check and T2.3's regression and key vectors, the key vectors' host fields held to each cell's own recording since the test author's 4edd4cf1. The two existing database jobs' unpinned `actions/setup-python@v7` are pinned by commit as every other use.
- **The Postgres provider's test** (`tests_test_ops/test_the_postgres_provider.py`) now runs in `native-test-ops`, which gains the pinned service, its DSN, `SDM_REQUIRE_POSTGRES`, psycopg and ADBC's SQLite driver; it returned without asserting there before. L5's test runs there too, at the floor, since the skip scan refuses an `--ignore` in a job that runs the core's tests.
- **L4** (`l4-goldens (duckdb|sqlite|postgres)`): `sdm-data`'s `tests/<database>_goldens.rs`, every statement the dialect renders for the contract cases pinned verbatim beside its request, with one shared module (`tests/goldens/mod.rs`): each golden must be what the dialect renders, and every fetch python-core's run of the cases on that database made (the reference cell's contract job, which executed each statement on the database and held its result to the reference's) must be a golden with its statements; a run named but missing, empty or holding no fetch on the database fails, and a failure prints each missing golden ready to paste. `duckdb_goldens.rs` (189) and `postgres_goldens.rs` (188) are new, collected from those runs' `core.fetches`; `sqlite_goldens.rs` (T2.2's, with T2.19's 96, 203 in all) gains the six `indexes` reads the cases make and no golden held. After the rebase onto T2.19, its eleven two-path cases' statements are goldens on all three databases (85 new on DuckDB and on Postgres), each run of all 97 cases held to them, and python-core and rust-host still agree with the reference on SQLite and Postgres.
- **L5** (`l5-conversion (floor-pandas2.2|dbr17-pandas2|ref-pandas3)`): `tests_test_ops/test_l5_conversion.py` on the test-ops build and the service, in every cell. A table of each type of the type map, built on DuckDB and loaded into SQLite and Postgres by the contract loader, is read through each provider and admitted by the core: each column's Arrow type is the recorded conversion table's, its values are what the database's own driver reads (DuckDB's, `sqlite3`, psycopg), and the types all three store as their own (int64, float64, string, binary) reach the core as identical Arrow; each type an engine stores in another form is the type map's and is printed per engine (KO2-47). The presentation table: each layout of the result the core hands the host (`predict.rs`), read by the host's own `_rows`, `_id` and `_as_answered` and presented by `to_pandas()`, gives the answer's JSON values and the recorded dtypes for the pandas major.

## T2.18

T2.18 is any column name (KO2-36): a column whose name holds a dot, a backtick or a line break is kept as data on the core route, and a query names it, on DuckDB, SQLite and Postgres.

### What changed

- **The parser holds the table and the column apart** (`sdm-pql`): a column node, a join's keys and an aggregation's group-by and time column carry a `ColumnKey` from the token to the validated query, so nothing splits a name on a dot (the sites the design names: `query.rs:42,341`, `ast.rs:310,709`, `sdm-core/src/pql.rs:559`, and every validator's `table_name`/`col_name`, now gone).
  A quoted name is any text between backticks, a backtick in it doubled and a line break kept as it stands (`lexer.rs`'s `quoted_id`, `names.rs`); a query is written back with each name quoted where a bare identifier cannot spell it.
  Messages still name a column as `table.column`; the key a target joins on is still the first by that text, as the reference sorts.
- **The core says what it resolved** (contract v26, optional, as T2.2's `key_dtype`): `Materialized.query`, `QueryFacts` (entity table, problem type, whether the target is windowed, a forecast's steps); the query's text is the state's.
  The v26 schema and lock entry are regenerated by the generator.
- **The Python host's core route** keeps every column the core described (`_rust/schema.build` builds each `SourceTable` without the old route's name check), and where a schema holds such a column, a query the old validator refuses is the core's to resolve as it gathers it (`_rust.materialize.Unresolved`, read back through `asked`); a forecast is kept in the steps the core asked; a ranking over candidates, which the host asks one part per candidate, is refused as the old validator refuses it.
  Every other query resolves as before, the shadow check kept, and python-core runs the core operations rust-host runs.
  Each change to frozen bridge code is declared in `bridge_changes.json` (E50).
- **The PQL quirk table's new readings**: its two rows whose spelling the reference refuses and the core reads (`backticks/unknown-with-dot`, `backticks/newline-inside`) are marked `core_only`, each held to the core's refusal by name (unknown table, unknown column) and to differing from the reference's recorded answer (`pql_quirks.rs`).
  The 417-query corpus holds no query the change moves.
- **L4 goldens**: the 27 requests the `name.*` cases make naming such a column, pinned with their statements on SQLite (`sqlite_goldens.rs`) and on DuckDB and Postgres (`name_goldens.rs`).
- **Register**: P2E-1 (permanent, KO2-36), P2E-2 (temporary, KO2-56, until T2.10: the filter cases), P2B-2 retired (rejected, citing KO2-36, ID kept); DuckDB baselines for the fifteen cases on the three runners.

### Deviations and questions

- **The filter role waits for T2.10.** The core refuses a target filter under its not-yet rule `target_filter` whatever the column's name, so the three `name.*-filter` cases and the twelve filter vectors cannot answer until T2.10 lands; P2E-2 registers them, and the acceptance tests that hold every role (step 2, each case through predict, rust-host's predict runs) stay pending for that role alone.
- **The comparator's KO2-36 differences** (above) need a judging change or an owner ruling before the gate passes these cases; no judging file is touched here.
- **The contract**: `Materialized.query` is a v26 addition, recorded as T2.2's was, as a deviation from all vocabulary in T2.1b.
- A query the core cannot resolve over a schema holding such a column is refused by the core's materialize (`INVALID_REQUEST`, field `query`), not with the old validator's diagnostics; the code is the same.
- `record_quirks.py` would drop the `core_only` marks on a re-record; the quirk test then fails on the two rows, by name.

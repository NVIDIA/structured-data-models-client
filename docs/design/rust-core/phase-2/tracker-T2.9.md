## T2.9

T2.9 is forecasting's options on top of the split already in the core (E153): `num_forecasts`, `lag_timesteps`, quantiles, and `response_field` for quantiles, on both hosts and DuckDB, SQLite and Postgres.

### What changed

- **Quantiles**. `sdm-wire` reads an item's `quantiles` as the bindings' `_float_dict` reads it (an object, each value a finite number or text a float reads; refusals name `prediction.quantiles`), keeps it as the mapping `response::mapping` gives, each value written as the double it reads as, so the core's `response_field` refusal of it is gone.
  `sdm-request`'s layout keeps each answer's quantiles through a merge of calls and a forecast's steps; the result's `quantiles` column is the JSON object text of each answer's mapping in a Utf8 column (the one encoding of a mapping-valued field, T2.8's), `{}` where an answer gave `{}`, null where it gave none; `absent()` reports `quantiles` only where no answer holds any.
  The Python host reads each row's quantiles with the same `_mapping` as the explanation and metadata and hands them to `PredictionItem`, so `to_pandas()` spreads them as `quantile_<key>`, as on the old route.
- **`lag_timesteps`** (`9e1deb95`). The value travels in `Materialize.values` (contract v27) and is read by `sdm-request`'s `AskedLag` as the reference's engine meets it: negative, or not ordered against zero (text, null, a list), refused for any query; not whole (a float, `true`) or past `u64` refused for a temporal query; otherwise the steps a temporal query adds, none for a static one (which the reference takes and ignores).
  `sdm-core` refuses it where the engine does, once the context is labelled, so the statements before the refusal are the reference's.
  For a temporal query, `sdm-core/src/lag.rs` moves each example's anchor back by the steps' windows (a month's by the calendar, as pandas multiplies a `DateOffset`), reads the aggregated table's rows from there in one `_by_time` read (the context's examples before narrowing, then the entities predicted for, as the reference's `sample_lagged_target`), and lays out `__kumo_arl0__` to `__kumo_arl<n-1>__`, each the target labelled by `sdm_engine::labels` over the window that many steps back.
  `sdm-request`'s payload puts them after the label in both halves with no semantic type: an aggregation's `float64`, a condition's `bool` (`float64` where no example has one).
  A payload the lags would make larger than the endpoint takes is refused before any column is computed.
- **Contract v27** (the working version, T2.12's): `Materialize.values` carries `lag_timesteps`; it leaves `Materialize.options`' names; `Predicted.result`'s `quantiles` column is a mapping-valued field, JSON object text in Utf8, in place of v26's list of float structs, which could neither keep a key as written (`"0.50"`) nor hold one that is not a number, both of which the reference's `quantile_<key>` columns keep.
  The schema regenerated (descriptions only); the lock line unchanged.
- **`num_forecasts`**: no product change; E153's split answers every `num_forecasts` case, now with lags and quantiles per step.
- **rust-host** (`76172f28`, protected `sdm-testkit/src/host.rs`): a case's `lag_timesteps` goes into the call's values as written, predict asks the case's `outputs`, and the scripted endpoint answers probabilities and quantiles where the case asks.
- **Judged data**: the census's `rule:lag_timesteps` probe taken out (its site is gone); bridge changes declared `moved` (`_rust/materialize.py::<module>`, `_rust/predict.py::predict`); baselines for the 26 cases on all three runners (`ratchet.py accept --checkpoint c8075715`); 17 L4 goldens per database.

### Deviations and questions

- **An average's, a minimum's or a maximum's lag on its own row** (fix 1, decided by the orchestrator under KO2-70 on 2026-10-19).
  The reference's executor labels a lag through `execute_join`, which drops the examples whose window holds no value, and the engine's frame of the lags lines the rest up by position, so each value moves to the first examples rather than its own, and the last examples get none (shown: user 0's predicted row at 2023-08-01 gets no lag where its window holds 112.0).
  The core puts each value on its own example (`lag.rs`'s `Lag::columns`, by the labels' mask), so these columns differ from the reference's; a sum's, a count's and every comparison of them are unchanged.
  Held by `lag.rs`'s `a_maximum_s_values_keep_their_rows_across_gaps` and `an_average_s_value_is_on_its_own_example`, and the route test `test_an_average_s_lag_is_each_row_s_own_window` (each predicted row's lag its own window's average, read from the data; nothing else of the request differs from the old route's).
  The 40-source differential after the fix: every payload difference is an average's, a minimum's or a maximum's lag column (or a comparison of one), none elsewhere.
  Its register entry waits for an ID (lane b's block, P2B-1 to P2B-19, is spent) and for KO2-70 on the phase head, as does P2B-19's approval.
- **Wording of the refused lags** (the orchestrator's note): the reference refuses `-1` with its engine's own sentence (`'lag_timesteps' cannot be negative (got -1)`), and `1.5`, `2.0` and `true` (`unsupported operand type(s) for *: 'float' and 'DateOffset'`) and `"2"` (`'<' not supported between instances of 'str' and 'int'`) with Python's TypeError text, all `INVALID_REQUEST`.
  The core route gives the same code and class, details `field: lag_timesteps` and `reason` (`negative`, `not_a_whole_number`, `not_a_number`), and the Python host says plainly: "lag_timesteps is how many past steps of the target are added as features, a whole number of zero or more; this one is refused (<reason>)" (`_rust/errors.py`'s `WORDED`; test `test_a_refused_lag_is_said_plainly_under_the_reference_s_code`).
  A lag past the time range is said as "lag_timesteps reaches further back than a time can be held (before 1677); ask for fewer steps" (P2B-18). The cases hold codes, not messages (H17).
- **P2B-18** (approved by both round 1 reviewers, recorded at the orchestrator's direction): a lag reaching outside what a time holds, or past `u64`, is refused `VALUE_OUT_OF_RANGE` naming `lag_timesteps`, where the reference's engine overflows and its client says `INTERNAL_ERROR`.
- **P2B-19** (approved, KO2-70, decided by the orchestrator under the owner's standing delegation): a NaN or infinite `lag_timesteps` (a float, or a `Decimal`) is refused `INVALID_REQUEST` on the core route by name, before anything is read; the reference adds no lag for a NaN, refuses an infinity after labelling, and fails `INTERNAL_ERROR` on a `Decimal` NaN. Diagnostic test `test_a_nan_lag_is_refused_on_the_core_route_only` (NaN, +inf, -inf).

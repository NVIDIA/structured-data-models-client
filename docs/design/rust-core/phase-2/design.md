## Architecture choices new in this phase

Phase 1's mechanisms are reused as built: the contract and its lock (`P1 d:100-125`), the data port (`P1 d:136-167`), runners and cells (`P1 d:319-360`), comparator (`P1 d:362-378`), ratchet and checkpoint (`P1 d:380-396`, H2, E131(f)), register v2 (`P1 d:398-404`), coverage (`P1 d:406-411`), gate (`P1 d:436`), lanes and landing (E43, E130, E131), the bridge freeze (`P1 d:249-258`), the evidence pack (`P1 d:528-541`).

1. **One contract bump, v26, in T2.1b** (lesson 14; H4). All of Phase 2's vocabulary goes in it:
   - paging: a `Fetch` result may carry a continuation, and the core asks again until the provider says it is done; nothing is truncated silently (plan section 3, "The provider contract"), replacing Phase 1's "drained whole" (`P1 d:145`);
   - multi-column keys in `Neighbors`, `Lookup` and key sets (for `composite_key`), replacing the single `key: String` (`sdm-contract/src/data.rs:261-279`);
   - ranking and forecast result fields;
   - `main`'s multi-call `predict`: several model calls per request in `RequestState`, the per-call and per-request limits, and an error's answered-parts fields;

2. **Every case on all three databases** (KO2-19; T2.1a).
   A case runs on DuckDB, SQLite and Postgres unless its file says otherwise, and no case file may say otherwise without an owner-approved exclusion; the case format gains the fields Phase 1's could not carry (`candidates`, `top_k` on a forecast; E153), with accept and refuse vectors in `contract/tests/malformed-cases.json` run by both loaders (`P1 d:581`).
   - **Data.** SQLite and Postgres bases are loaded from the DuckDB-built tables through Arrow by one contract loader, with a per-engine type map (part of T2.1a's vectors); the reference and both core hosts read the same loaded database.
     The map uses an engine's own type wherever it has one (for example Postgres `numeric`, arrays, composite types or `jsonb`) and stores a type the engine lacks as the map says (for example JSON text for a nested value, and a SQLite decimal in a column declared `TEXT`, since a column declared `DECIMAL` takes numeric affinity and rounds what it stores).
     The type map is T2.1a's `contract/type-map-vectors.json`, judging data under the existing `contract/*-vectors.json` protection, with two decimal keys equal to 15 significant digits that must stay distinct after loading on SQLite (KO2-35) and two equal keys of different scales, `DECIMAL(10,2)` and `DECIMAL(12,4)`, that must still join (lesson 19); the type map's vector is the one definition of a decimal's canonical text (plain positional notation, no exponent, no trailing fractional zeros, no trailing point, `-0` written `0`), which the Python loader and the Rust key binders each implement and both run, so equal values have one text, with `100.00` and `100`, and `-0.00` and `0`, in the vector too.
     Check 1 (L2) compares the core and the reference on each engine's stored input, whatever it is; check 4 (L5) is separate and judges the core's conversion of each engine's stored types to Arrow without loss of value or metadata.
     Every non-native mapping is listed in the evidence of checks 1 and 4, and a cell an engine can't store is never counted as covered by its replacement: coverage S1's matrix holds no cell for a type an engine can't store, derived from the type map's non-native entries, never written by hand (lesson 8), with a seeded fault (a type an engine stores, declared absent, fails), and the evidence lists each such absence per engine, so check 1 can't fail by construction (Q-L5).
     No case is skipped: an input an engine can't load is a proposed exclusion for the owner, named in check 1's evidence, and the locked run fails on that case until the owner answers.
   - **Reference.** The recorder (test-author role) records the reference for every S1 case on each database on this Linux machine (KO2-2), one reference line per case and database; the three runs are independent and run in parallel.
     SQLite and Postgres lines are keyed `<case>@sqlite` and `<case>@postgres`, and DuckDB lines keep the bare case ID, and observations and baselines use the same keys (orchestrator's decision).
     Today's harness reads only bare case IDs (the observation schema's case pattern, `compare.py`'s known-case check, the ratchet's removed-case and baseline rules), so T2.0f teaches all of them the suffix before T2.1a records any suffixed line.
     The core's SQLite and Postgres observations arrive with T2.2 and T2.3, and the ratchet holds each from its first admission.
   - **CI.** Each `contract-python` cell runs once per database as its own job, `contract-python (<cell>, <database>)`, and `cross-host` once per database, `cross-host (<database>)`: nine and three parallel jobs where there are three and one today.
     Only the Postgres `contract-python` jobs start the pinned Postgres service; `cross-host (postgres)` replays (KO2-20).
     Each job runs today's case count, so a push's wall time stays about today's (43 to 88 minutes, plus a minute for the service), while those jobs' runner minutes triple.
     `rust-test`, where rust-host's observations are made, runs the case set three times in one job until CI5 splits out `rust-host`; T2.1a records every job's timings.
     A job that runs no case on its database fails, so a leg can't pass empty.
     One rule, defined once in T2.1a's runner and used by both `gate.sh` and CI, stages the core on a database: the runner runs the core legs (python-core, rust-host and the Python provider kit) on a database exactly when the core under test reports a provider for it, through a private, plain-data marker (a list of database names in the private native module for python-core and the Python kit, and the test kit's provider list for rust-host, which holds the dev-only `rusqlite` provider), never public API, and otherwise the reference side only (the old client over the loaded database, checked against the committed reference lines, and the comparator's controls), so a job still runs cases (orchestrator's decision); the ratchet's "baselined, and not observed" rule (`check_baselines`) stops a later candidate dropping a provider once its legs are admitted.

12. **The table source** (metric-view groundwork, KO2-39), held to KO2-46: only what Phase 2 uses, as plain data any host language expresses.
    Today each schema table has a source name, `source: String` in the described and held schema (`sdm-contract/src/ops.rs:380-415,533-534`), and every data request names that source as `table: String` (`sdm-engine/src/graph.rs:24-27`, E61(a)), quoted as one identifier (`sdm-data/src/duckdb.rs:725-757`).
    A metric view needs four things more (`main`'s `engine/rfm/backend/databricks/table.py:136-205`, 18e26f1c): a name of up to three parts, each quoted alone; columns renamed to the view's spelling; columns that are SQL expressions; a SQL row filter.
    v26 makes the one change that reshapes existing fields, and nothing more:
    ```rust
    pub struct Relation { pub source: Vec<String> } // 1 to 3 name parts, each quoted alone, never split on dots
    ```
    - `Relation` replaces the schema's per-table `source: String` and every data request's `table: String`, so each request carries what it reads and a host provider (T2.7's non-SQL provider, the rust-host replay and `rusqlite` providers) needs no state per run; two schema tables over one source are two equal relations.
    - Phase 2 hosts give one part, so a dotted name still reads as one table (a golden shows it) and no S1 answer moves; `sdm-data` renders every dialect's `FROM` from a relation through one function, each part quoted alone.
      Each dialect declares how many parts it accepts (DuckDB 1 to 3; Postgres 1 or 2, schema and table; SQLite 1 or 2, the first naming `main` or an attached database, as in `["main", "t"]`), with executed goldens only for those forms; a relation with no part or more parts than its dialect accepts is refused by name (rule `relation`, a negative vector per dialect, and a provider-level census probe).
    - It is a record holding a list of strings, built from Python and Java as easily as today's string.
    Phase 3 adds, as optional fields with defaults, so no existing field changes shape again: `columns` (each a schema name with a source column or a SQL text expression), a SQL text `filter`, a provider capability for such derived relations (a provider without it refuses one by name), and a failure class on `ProviderError` set by the provider from its driver's codes; request column names then become the schema's, mapped by the provider through the relation each request carries.
    The rules that bound that addition hold now: SQL text is opaque to the core and rendered only by `sdm-data`'s dialects; the core never matches error text; dialect logic stays in `sdm-data` (L0 keeps dialect terms out of `sdm-schema`, `l0_scan.py:1050-1086`), which in Phase 3 reads a view definition into a dialect-free view model internal to the Rust crates, and `sdm-schema` interprets only that model (plan section 3: "view retrieval per source", "source-neutral view interpretation").
    Why this shape: the one field that must change type changes once, in the single bump; everything else a view needs is additive, so it waits until Phase 3 uses it, and SQL never enters the typed request vocabulary a non-SQL provider (T2.7) must read.
    A Snowflake semantic view takes the same additions rendered by its own dialect; Lakebase is Postgres with plain relations; frames (Phase 4) take plain relations only.
    Cut in fix 13 under KO2-46 (tracker): the defined-but-refused `columns`, `filter`, `SqlText` and `ColumnFrom`, the `derived_relations` capability and the `FailureClass` field.

### Locked acceptance checks

Each is falsifiable: it passes on the candidate and fails on the seeded fault named, as Phase 1's were (`P1 d:555-564`; H26).
